# OpenMP Runtime Trial 数据集构建方法论与复用规范 v0

## 1. 文档目的

本文档抽象当前 PolyBench/C 数据集构建流程，作为以后迁移到其他 benchmark suite 时的参考规范。

适用对象包括但不限于：

```text
PolyBench/C
NAS Parallel Benchmarks 的 C/OpenMP 变体
Rodinia 中适合 CPU/OpenMP 的 kernel
自建 C/C++ numerical kernels
其他可构建 correctness reference 的 benchmark
```

本文档关注的是 OpenMP runtime action-performance trial dataset，不是普通源码数据集。

## 2. 数据集的基本样本形态

最终 raw trial dataset 的核心样本应表达为：

```text
program + input + platform + runtime action
    -> correctness + runtime + speedup + reward
```

更具体地，一个 trial row 至少应包含：

```text
program_id
program_family
source_version
program_variant
input_id 或 dataset_macro
platform_id
compiler
openmp_runtime
runtime_action
correct
timeout
runtime_sec 或 runtime_median_sec
runtime_std_sec
runtime_cv
baseline_runtime_median_sec
speedup
reward
```

其中 `runtime_action` 在当前项目中主要是 OpenMP runtime 环境变量，例如：

```text
OMP_NUM_THREADS
OMP_PROC_BIND
OMP_PLACES
OMP_SCHEDULE
OMP_DYNAMIC
OMP_WAIT_POLICY
OMP_MAX_ACTIVE_LEVELS
```

## 3. 核心原则

### 3.1 程序变体必须受控

当前任务不是让模型自由改写源码，而是研究 OpenMP runtime 参数对性能的影响。

因此源码处理必须受控：

```text
原始源码
    -> 受控 OpenMP pragma 标注版本
    -> runtime action trial
```

不应在同一个 program variant 中混入：

```text
算法重写
数据结构重写
循环重排
blocking/tiling
SIMD 改写
compiler flag tuning
```

如果未来确实需要这些版本，必须单独建 program variant，例如：

```text
manual_omp_v0
collapse_v1
rewrite_v1
tiling_v1
```

并在 registry 中显式记录。

### 3.2 原始源码与工作源码必须分离

推荐目录约定：

```text
workloads/<benchmark>/<version>/original/
workloads/<benchmark>/<version>/omp_v0/
```

其中：

```text
original/  保存未修改的上游源码
omp_v0/    保存当前 OpenMP 标注版本
```

这样 reference 可以始终从 `original/` 生成，避免因为 OpenMP 标注错误污染标准答案。

### 3.3 正确性先于性能

任何 runtime trial 进入数据集前，都必须先有 correctness gate。

推荐流程：

```text
1. 编译 sequential reference binary。
2. 运行 reference binary，保存输出或 checksum。
3. 编译 OpenMP binary。
4. 在 baseline OpenMP action 下运行 correctness check。
5. 后续每个 action trial 都需要记录 correct / incorrect / timeout。
```

性能数据必须以正确性为前提。错误结果的运行时间不能作为有效优化目标。

### 3.4 输入规模必须可追踪

输入规模会强烈影响 OpenMP runtime tuning 的结论。

对每个 benchmark，应明确记录：

```text
input_id
dataset_macro
problem_size
selected_dataset_reason
baseline_runtime_median_sec
input_size_status
```

不要只记录“跑了某个程序”，必须知道它跑的是哪个规模。

## 4. 推荐工程目录结构

一个 benchmark 数据集建议使用如下结构：

```text
datasets/<dataset_name>/
  config/
  registry/
  plans/
  external/
  workloads/
  build/
  references/
  trials/
  reports/
  scripts/
  logs/
```

各目录职责如下：

```text
config/
```

保存平台信息、action space、baseline action、测量策略。

```text
registry/
```

保存 program registry、action registry、kernel 状态、source path、variant 信息。

```text
plans/
```

保存 trial plan。trial plan 应该是可复现的静态文件，而不是临时手写循环。

```text
external/
```

保存上游压缩包、下载记录、校验信息。

```text
workloads/
```

保存原始源码和 OpenMP 变体源码。

```text
build/
```

保存编译产物，不应把 build artifact 当成 source of truth。

```text
references/
```

保存 sequential reference 输出、checksum 或 oracle。

```text
trials/
```

保存 correctness 运行结果、Round 0、Round 1、formal trial 数据。

```text
reports/
```

保存 annotation review、correctness report、noise report、progress report。

```text
scripts/
```

保存可复现脚本。脚本应默认 dry-run 或提供明确安全边界。

## 5. Program Registry 设计

每个 kernel 或 program 至少应登记：

```text
program_id
program_family
kernel_name
source_dataset
source_version
language
category
source_file_original
source_file_omp_v0
openmp_variant
openmp_status
num_omp_parallel_for
schedule_runtime_enabled
has_reduction
has_collapse
has_nested_parallel
has_task
selected_dataset_macro
input_size_status
baseline_runtime_median_sec
split
```

`openmp_status` 建议至少包含：

```text
ready
partial
excluded_v0
failed_compile
failed_correctness
too_short
too_slow
too_noisy
```

含义建议如下：

```text
ready
    标注较完整，正确性通过，后续可进入 trial。

partial
    只安全并行化一部分 loop，但仍可进入 trial。

excluded_v0
    当前 v0 阶段不安全或不适合处理。

failed_compile
    编译失败。

failed_correctness
    OpenMP 输出不正确。

too_short
    runtime 太短，噪声占比高。

too_slow
    runtime 太长，采集成本过高。

too_noisy
    多次运行波动过大。
```

## 6. OpenMP 标注规范

对于从 sequential C/C++ 转换来的 benchmark，v0 阶段建议只允许：

```text
#pragma omp parallel for schedule(runtime)
```

必要时允许：

```text
private(...)
reduction(...)
```

不建议在 v0 阶段引入：

```text
collapse
task
nested parallel
simd
critical/atomic 大量改写
算法级重写
```

标注位置建议限制在：

```text
kernel_* 函数内部
```

这样可以降低 benchmark harness、初始化、输出、计时逻辑被意外改变的风险。

## 7. Action Space 设计

当前单平台 v0 可以使用 absolute action space，例如：

```text
OMP_NUM_THREADS in {1,2,4,8,16,32,48,64}
OMP_PROC_BIND in {false,true,close,spread}
OMP_PLACES in {threads,cores,sockets}
OMP_SCHEDULE in {static,dynamic,guided,auto}
OMP_DYNAMIC in {FALSE,TRUE}
OMP_WAIT_POLICY in {PASSIVE,ACTIVE}
OMP_MAX_ACTIVE_LEVELS in {1}
```

但必须由当前平台 profile 约束。例如当前容器只可见 64 个 logical CPUs，就不应使用 96 或 128 线程作为默认候选。

长期跨平台时，可以额外派生 normalized features：

```text
threads_ratio_physical_cores
threads_ratio_logical_cpus
threads_per_socket_ratio
threads_per_numa_ratio
```

这样既保留当前真实 action，又方便未来迁移。

## 8. Reference 与 Correctness 策略

每个 benchmark 必须能回答：

```text
什么是这个程序的正确输出？
如何从 sequential 原始版本得到 reference？
OpenMP 版本的输出如何比较？
```

推荐策略：

```text
1. 从 original/ 编译 reference binary。
2. 使用固定 input 或 dataset macro 运行 reference。
3. 保存 live-out arrays、checksum 或标准输出。
4. 从 omp_v0/ 编译 OpenMP binary。
5. 在 canonical baseline 下运行 OpenMP binary。
6. 与 reference 做数值比较。
```

浮点输出通常不建议 byte-level diff，建议使用：

```text
abs_tol = 1e-6
rel_tol = 1e-5
```

整数输出可以 exact match。

如果程序存在 OpenMP reduction 或调度顺序变化，可能需要按 kernel 调整 tolerance，但必须记录原因。

## 9. Input Size 选择方法

输入规模选择不能拍脑袋，应通过 baseline runtime profiling 决定。

推荐流程：

```text
1. 先选一个中大型默认规模。
2. 编译并运行 canonical baseline。
3. 统计多次运行 median/std/cv。
4. 如果 runtime 太短，增大输入规模。
5. 如果 runtime 太慢，减小输入规模。
6. 最终把选择结果写回 registry。
```

当前 PolyBench/C 的默认起点是：

```text
LARGE_DATASET
```

候选包括：

```text
MINI_DATASET
SMALL_DATASET
MEDIUM_DATASET
LARGE_DATASET
EXTRALARGE_DATASET
```

推荐目标窗口：

```text
baseline median runtime: 0.5s - 30s
宽松接受范围: 0.2s - 60s
```

## 10. Trial 分阶段策略

不建议一开始就对所有 action 做完整采集。

推荐分阶段：

```text
Stage A: static validation
    检查 registry、源码路径、action space、脚本。

Stage B: compile check
    检查 OpenMP 标注是否能编译。

Stage C: correctness check
    检查 baseline OpenMP 版本是否输出正确。

Stage D: input size profiling
    确定每个 kernel 的最终输入规模。

Stage E: Round 0 sanity trials
    每个 kernel 少量 action，检查 timeout、correctness、噪声、harness。

Stage F: Round 1 formal trials
    对通过质量门槛的 kernel 采集正式 action-performance 数据。
```

## 11. 数据质量过滤

正式进入训练数据导出前，至少过滤：

```text
compile_success == true
valid_action == true
correct == true
timeout == false
runtime_median_sec > 0
baseline_runtime_median_sec > 0
runtime_cv <= 0.05
```

对少数天然波动较大的 kernel 可以放宽到：

```text
runtime_cv <= 0.10
```

但必须显式标记。

## 12. Reward 设计

当前建议 correctness-gated reward：

```text
如果 correct == false:
    reward = penalty
else:
    reward = log(speedup)
```

其中：

```text
speedup = baseline_runtime_median_sec / runtime_median_sec
```

这种设计能避免模型为了速度推荐错误结果。

## 13. Split 规则

训练、验证、测试划分必须按 program 或 program_family 划分，不应按 trial row 随机划分。

错误做法：

```text
同一个 kernel 的不同 action 一部分进入 train，一部分进入 test。
```

正确做法：

```text
一个 kernel 的所有 action trial 全部属于 train / val / test 中的一个 split。
```

如果同一个 program_family 有多个源码变体，也应避免变体之间泄漏。

## 14. 运行环境与硬件边界

数据集构建过程中必须记录但不随意改变：

```text
CPU 型号
visible CPUs
cpuset
NUMA topology
compiler
OpenMP runtime
container 信息
```

除非实验方案明确要求并得到确认，否则不要修改：

```text
CPU governor
turbo
BIOS
cpuset
系统级 affinity
服务器状态
```

在 CPU 被其他任务占用时：

```text
可以做 dry-run、静态检查、轻量编译。
不建议做 correctness 运行和性能 trial。
绝不能把繁忙状态下的 runtime 当作正式性能数据。
```

## 15. 迁移到新 benchmark 的最小 checklist

迁移到新 benchmark 时，至少完成：

```text
1. 固定 benchmark 版本和来源。
2. 保存 original/ 原始源码。
3. 建立 omp_v0/ 受控 OpenMP 变体。
4. 建立 program registry。
5. 明确每个程序的 input size 候选。
6. 明确 reference 输出生成方法。
7. 明确 correctness comparison 方法。
8. 建立 action space。
9. 建立 canonical baseline。
10. 编译检查。
11. 正确性检查。
12. input size profiling。
13. Round 0 sanity trials。
14. Round 1 formal trials。
15. 质量过滤与 split freeze。
```

只有这些信息都可追踪，后续从 raw trial dataset 派生 SFT / DPO / eval 数据才可靠。
